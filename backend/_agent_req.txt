AI Agent 功能优化需求说明
CRM-OKR 系统(AI 智能助手方向)    版本:v1.0    日期:2026-10-08
涉及仓库:Recrm(后端) / Recrm-Frontend(前端)    环境:生产 zhongtaixuding.cn
一、背景与现状(基于生产环境实测)
AI 智能助手已完成第一期建设并通过实测,能力底座是完善的,当前的核心问题不是"功能不够",而是"用不上、看不到"。

1.1 已有能力(实测通过)

1.2 关键问题(实测发现)

1.3 业务数据体量(用于判断优先级)


二、优化目标
让 AI 出现在领导和同事"已经在的地方"(飞书),而不是要求他们登录系统
展示只有 AI 能提供的价值:主动洞察、跨模块串联、自然语言取数
所有内容必须有事实依据,宁可少说,不可编造
沿用现有 RBAC 权限体系与写操作确认机制,不新增越权路径
三、需求清单(按优先级)
优先级定义:P0=先做,投入产出比最高;P1=第二阶段;P2=按需推进。

3.0 前后端分工速览

小结:P0、P1 为纯后端工作(且不与前端页面耦合,可独立交付);P2、P4 以前端页面为主 + 少量后端接口;P3 不依赖开发编码。

P0-1  领导「每日经营简报」(飞书推送)
现状:数据都在系统里,但需要领导主动登录查看;无任何主动触达。
需求:每天早上 8:30 自动生成一条经营简报,通过飞书私聊推送给董事长/总经理/中心负责人。
内容结构(每条都必须来自工具取数,AI 只负责措辞):
昨日概览:新增线索、新增客户、成交/签约、项目交付进展
风险提示:停滞项目、超期未交付排期、卡住的审批单
今日待办:待该领导审批的单据数量与明细
异常提醒:考勤异常、考核未提交人数(可选)
实现要点:
取数:复用 app/services/ai_scene.py 的工具调用方式(agent_runtime),新增聚合函数;数据源 leads / customers / opportunities / contracts / projects / schedules / approval_instances / feishu_attendance_daily
生成:先取事实(facts),再交给 LLM 润色为 3~5 条要点;LLM 不可用时降级为纯事实列表(沿用现有 is_llm_configured 判断)
推送:复用 app/services/feishu_notify.py 私聊推送(注意:发送前需按要求清理代理环境变量)
收件人:做成配置(建议按角色 center_lead / chairman / gm 或白名单 open_id 配置)
调度:每天 08:30;服务器已有 cron 环境,可与现有每日 02:00 备份调度方式一致
审计:写入 ai_scene_runs(scene=exec_briefing),记录 tokens / elapsed_ms / cost
验收标准:
每天 8:30 收件人收到私聊简报,格式统一、无英文
抽查任意 3 个数字与系统内数据一致(不允许出现夸大/编造)
当日无数据时输出"暂无数据"而不是留空或编造
LLM 不可用时能降级推送纯事实版,不中断

P1-1  飞书 AI 助手(双向对话)
现状:飞书仅单向通知(审批流转/催办/结果),无接收消息能力(代码中无 event_callback / im.message.receive 处理)。
需求:在飞书里直接向机器人提问,由现有 Agent 回答。例如"这个月线索多少""XX 项目到哪了""谁还没交考核"。
实现要点:
飞书开放平台:开通事件订阅(im.message.receive_v1)+ 配置回调地址(建议 https://zhongtaixuding.cn/api/v1/feishu/events)+ 权限 im:message / im:message:send_as_bot;回调需处理 URL 校验(challenge)与验签
后端:新增飞书事件处理路由;收到消息后立即返回 200,再异步调用 Agent,最后用 im/v1/messages 回复
会话映射:飞书 open_id ↔ agent_conversations.public_id(现有 56 位用户已绑定 open_id,可作为用户识别入口)
权限:复用现有 RBAC,工具调用沿用 required_permission 校验;建议领导默认只读(写工具禁用或强制二次确认)
安全:建议按 open_id 白名单限量开放首版,避免全员误用与成本失控
审计:每次对话写入 ai_scene_runs(scene=feishu_agent),记录 tokens / cost
验收标准:
飞书内提问能收到基于真实数据的回答,全部中文
非白名单用户提问得到礼貌拒答
写操作在飞书内不可直接执行(或必须走确认流程)

P2-1  审批「AI 预审卡」(领导审批提效)
现状:已有 GET /api/v1/approvals/{id}/precheck(纯规则 facts-v1),领导审批仍需自己看字段判断。
需求:审批详情页顶部展示一张 AI 预审卡:业务背景摘要、同类历史审批如何处理、风险关注点、需要补充的材料。
实现要点:
复用 precheck_approval 的规则结果(不重复实现风控逻辑),在规则结果之上增加一段 LLM 摘要
接口:可在现有 precheck 接口上加参数(如 ?with_ai=1)或新增字段,避免破坏既有调用方
前端:审批详情页新增卡片组件;加载中/失败/无 AI 三种状态都要有兜底
红线(必须遵守):
文案中不得出现"建议通过/建议驳回"等结论性表述,只列事实与关注点
AI 不替代人工审批,不参与审批流转判定
验收标准:
审批页能看到预审卡,内容与规则 facts 不矛盾
文案无结论性措辞;AI 不可用时卡片降级为规则版或隐藏

P3-1  知识库内容从 0 到 1
现状:知识库表结构完备(knowledge_sources / knowledge_article_versions / knowledge_asks / knowledge_gaps),但已发布条目为 0,导致问答只能返回"未在已发布知识中找到足够依据"。
需求:让知识库有内容,使问答可用。
实现要点:
首批素材(系统内已有):133 张审批单与 27 张工单的标题/说明文本,可提炼为"这类业务怎么走"的条目
人工整理制度/流程/规范文档后录入(沿用现有知识条目审核流)
可选:接飞书云文档同步(需申请文档读取权限),实现自动入库与更新
验收标准:
提问公司制度类问题(如"报销流程")能得到有出处的回答,answer_mode 由 retrieve 变为模型生成
回答必须带引用标题与版本;无依据时明确拒答

P4-1  销售「AI 跟进助手」(使用频次最高)
现状:线索 117 条 / 跟进 133 条,是系统内最活跃的业务流;跟进建议需人工判断。
需求:线索详情页提供一键"生成下一步跟进建议";支持"拜访前生成客户背景卡";跟进可直接写入(走确认)。
实现要点:
复用工具:get_followup_records(读取历史跟进)+ add_lead_follow_up(写跟进,需确认)
前端:线索详情页新增按钮与结果面板;写入前必须走现有确认对话框
权限:沿用 lead:view(看)/ 写操作沿用既有权限校验
验收标准:
一键生成建议,内容引用历史跟进事实
写入跟进前有确认,未确认不落库

四、明确不做(避坑)

五、通用技术要求(所有需求适用)
语言:全部输出简体中文,禁止英文句子或英文过渡语(提示词已在 app/agent/prompts.py 加最高优先级语言要求,请保持)
计量:每次大模型调用写入 ai_scene_runs,记录 scene / tokens / elapsed_ms / cost,便于成本核算与审计
降级:大模型不可用或超时(现配置 45s)时必须降级为事实模式,不得报错中断主流程
权限:一律走现有 RBAC(user_can / required_permission),不新增越权路径
审计:AI 产生的建议类内容应可追溯(至少记录来源数据与时间)
性能:飞书回调必须在 3 秒内响应(先回 200,再异步处理),避免事件重试风暴
六、排期建议(供排期参考,非硬性承诺)


建议先交付第一阶段:投入最小、领导感知最强、不需要任何使用习惯改变。拿到反馈后再推进第二阶段。
