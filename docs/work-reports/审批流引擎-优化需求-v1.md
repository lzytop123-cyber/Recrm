# 审批流引擎优化需求（v1）

> 提给 Cursor 执行。本文档自包含，无需回读上下文对话。
> 目标：修复引擎并发/安全/兜底缺陷、清理重复代码、把"配了不生效"的能力（超时/催办/AP-21）真正落地。

---

## 0. 背景速览

系统里有个通用审批流引擎（`backend/app/services/approval_flow.py`），核心模型 `ApprovalInstance` + `ApprovalTask`（`backend/app/models/approval_flow.py`）。目前 21+ 条流程（AP-01/02/03/04/05/06~11/12/13/15/16/17/18/19/20/22/23/24）已端到端接通，唯一 **AP-21 资产赔偿（`asset_compensation`）** 缺回调分派。

术语：
- **G-08**：发起人不能审批自己发起的单据。
- **admin**：拥有 `admin` 角色的系统管理员，具备"代审"能力（`_is_flow_superuser`）。
- **blocked**：节点无可用审批人时，实例挂起等待人工介入（非驳回）。

## 1. 修 admin 兜底遮蔽"角色缺人应挂起"（**P0 · 正确性**）

### 问题
`_role_holder_ids` 的 docstring 明确写"系统管理员(admin)不作为审批兜底（职责分离，见配置表 sysadmin 说明），只有规则显式列出 admin 才会命中。"

但 `_resolve_task_candidates` 里，一旦某角色 holder 为 0 或只有发起人一人，直接把 admin 塞成候选人：

**文件**：`backend/app/services/approval_flow.py`
**位置**：`_resolve_task_candidates`（约 320–359 行）

```python
if not all_ids:
    su = _flow_superuser_ids(db)
    if su:
        return su, "ok"          # ← 这里把 admin 当业务审批人
    return set(), "blocked"
eligible = all_ids.copy()
if instance.initiator_id is not None:
    eligible.discard(instance.initiator_id)
if eligible:
    return eligible, "ok"
su = _flow_superuser_ids(db)
if su:
    return su, "ok"              # ← 同上
if instance.initiator_id in all_ids:
    return set(), "skip_g08"
return set(), "blocked"
```

### 影响
- AP-24 里 `center_lead` 角色未建时，节点不该被跳过、也不该由 admin 顶包，应挂起等运维配角色。
- 时间线里的候选人展示函数 `_resolve_candidates_for_display`（约 1179–1200 行）又努力把 admin 从展示里剔除，两处逻辑互相矛盾。
- 违反职责分离：admin 静默参与业务审批。

### 期望行为
- 节点角色 holder 为 0 → **`blocked`**（不再落 admin）。
- 节点角色 holder 只有发起人 → **`skip_g08`**（按现有逻辑跳过）。
- admin 只保留"代审"通道：`_superuser_reopen_for_act` 已经为挂起单准备好了；`_user_can_act_task` 里 `_is_flow_superuser(user)` 也已直通。
- 节点角色里显式列出 `admin`（罕见）时正常命中，无需特殊化。

### 修改方案
1. `_resolve_task_candidates` 中删除两处 `su = _flow_superuser_ids(db); if su: return su, "ok"` 兜底分支。
2. 保留 `assignee_id` 分支（该分支不涉及 admin 兜底）。
3. 由此产生的挂起单，admin 通过 pending 列表能看到（`_load_open_for_superuser` 已包含 BLOCKED）并可代审。

### 验收
- 新增测试：某节点角色配 `["legal"]`、系统里 `legal` 角色 0 holder，start_instance 后 `instance.status == "blocked"` 且 `reject_reason` 有说明。
- admin 用户 pending 列表能看到该 blocked 实例、能对其 approve。
- 现有测试全绿。

## 2. `act()` 加乐观锁 / 行锁（**P0 · 并发安全**）

### 问题
**文件**：`backend/app/services/approval_flow.py`
**位置**：`act` 函数（约 580–640 行）

`instance.version` 只 `+=1` 写，从不读校验；无 `SELECT ... FOR UPDATE`。并发场景：
- 会签节点两位签署方同时点通过 → 两个 task 各自 flush，`_advance` 两次推进。
- admin + 真候选人同时点通过。
- 前端双击/网络重试。

### 期望行为
- 同一实例的 `act()` 串行化。任一并发第二个请求返回 409 或 425（`审批状态已被他人更新，请刷新后重试`）。
- 单元测试能可靠复现（不需要真并发，构造版本号偏差即可）。

### 修改方案（二选一，推荐 A）

**方案 A：显式版本号 + payload 携带**
1. `ApprovalActRequest`（`backend/app/schemas/approval.py`）增加可选 `version: Optional[int] = None`。
2. `approval_flow.act(...)` 增参 `expected_version: Optional[int] = None`。
3. `act()` 入口:
   ```python
   if expected_version is not None and instance.version != expected_version:
       raise HTTPException(status_code=409, detail="审批状态已更新，请刷新后重试")
   ```
4. `_act_instance`（`backend/app/services/approval.py`）把 `payload.version` 透传下去。
5. 前端 `ApprovalCenterView` 从 `item.meta.version` 里取版本号回传（该字段引擎已经放进去了，见 `_instance_to_item` 的 meta）。
6. 前端修改另开 PR，本次改动允许 `version=None`（保持后向兼容），但**审批中心走的接口必须传**。

**方案 B：DB 行锁（补充，不替代 A）**
在 `act()` 入口用 `db.query(ApprovalInstance).with_for_update().filter(id=instance.id).one()` 重新拿一次实例（同事务内），保证事务串行。SQLite 环境测试时用 `PRAGMA locking_mode` 或 skip；PG 生产真锁。

### 验收
- 测试：构造两个 `ApprovalActRequest`，第一次 approve 成功后，第二次带旧 version 提交 → 409。
- 现有测试传新 version 参数后仍全绿。

## 3. 回调派发改注册表，顺便修 AP-21（**P1 · 结构 + 缺陷**）

### 问题
**文件**：`backend/app/services/approval_flow.py`
**位置**：`_dispatch_callback`（约 692–828 行）

- 22 个 `if/elif`，每接一个业务都要动核心引擎（违反开闭）。
- **`asset_compensation` 没有分支** —— AP-21 规则已发布，一旦被真发起，终审后无任何业务动作，且未知 biz_type 目前是**静默 no-op**（无 log、无 audit）。

### 期望行为
- 业务模块导入时注册回调，引擎侧无需为新增业务改代码。
- 未注册的 biz_type 走终审时写一条 warning 级 audit（可通过 `AuditLog` 落库，action=`approval_flow_callback_missing`），便于运维发现"配了流程但没接回调"。
- 回调抛异常时写一条 audit（action=`approval_flow_callback_error`, detail 含 biz_type / exception message），再重抛，不吞。

### 修改方案

1. `approval_flow.py` 顶部加：
   ```python
   ApprovalCallback = Callable[[Session, "ApprovalInstance"], None]
   _CALLBACKS: dict[str, ApprovalCallback] = {}

   def register_callback(biz_type: str, fn: ApprovalCallback) -> None:
       _CALLBACKS[biz_type] = fn
   ```
   回调统一签名 `(db, instance, *, approved, withdrawn=False)` —— 现有所有 `on_*_result` 已是这个签名，无需改造。

2. 把 `_dispatch_callback` 改成：
   ```python
   def _dispatch_callback(db, instance, *, approved, withdrawn=False):
       fn = _CALLBACKS.get(instance.biz_type)
       if fn is None:
           _audit_system(db, instance, action="callback_missing",
                         detail=f"biz_type={instance.biz_type} 未注册回调")
           return
       try:
           fn(db, instance, approved=approved, withdrawn=withdrawn)
       except Exception as exc:
           _audit_system(db, instance, action="callback_error",
                         detail=f"biz_type={instance.biz_type} err={exc!r}")
           raise
   ```
   `_audit_system` 是新增的、无 user 的 audit 辅助（`user_id=None, username="system"`）。

3. 在每个业务模块 **模块底部** 注册：
   ```python
   # backend/app/services/finance.py 末尾
   from app.services import approval_flow
   approval_flow.register_callback("refund", on_refund_flow_result)
   approval_flow.register_callback("receipt", on_receipt_flow_result)
   approval_flow.register_callback("receipt_diff", on_receipt_diff_result)
   ```
   注意循环 import：这些 import 已经在业务模块里做，把注册语句放模块底部即可。

4. 需要注册的映射表（完整照抄，不遗漏）：

   | biz_type | 模块 | 函数 |
   |---|---|---|
   | refund | `finance` | `on_refund_flow_result` |
   | receipt | `finance` | `on_receipt_flow_result` |
   | receipt_diff | `finance` | `on_receipt_diff_result` |
   | contract | `contract` | `on_contract_flow_result` |
   | contract_activate | `contract` | `on_contract_activate_result` |
   | contract_terminate | `contract` | `on_contract_terminate_result` |
   | contract_modify | `contract_modify` | `on_contract_modify_result` |
   | asset_borrow | `asset` | `on_borrow_flow_result` |
   | asset_return | `asset` | `on_return_flow_result` |
   | asset_maintenance | `asset` | `on_maintenance_flow_result` |
   | asset_inventory_diff | `asset` | `on_inventory_diff_result` |
   | timesheet | `timesheet` | `on_timesheet_flow_result` |
   | project_no_contract | `project` | `on_project_no_contract_result` |
   | project_initiation | `project` | `on_project_initiation_result` |
   | project_handover | `project` | `on_project_handover_result` |
   | project_acceptance | `project` | `on_project_acceptance_result` |
   | project_settlement | `project` | `on_project_settlement_result` |

   | ticket_cross_accept | `ticket` | `on_ticket_cross_accept_result` |
   | schedule | `schedule` | `on_schedule_flow_result` |
   | role_change | `org` | `on_role_change_result` |

5. **模块加载入口**：确保所有上述模块在 `app.main` / `app.api.v1.__init__.py` 启动路径里被 import（多数已经因 router 而 import；`org`、`contract_modify` 需确认，若无则在 `approval_flow` 模块底部主动 import 一次触发注册）。

6. **AP-21 asset_compensation 回调（新增）**：
   - 位置：`backend/app/services/asset.py` 新增 `on_compensation_result(db, instance, *, approved, withdrawn=False)`。
   - 语义（对齐 AP-21 规则，见 `seed.py::APPROVAL_RULES`）：
     - `withdrawn` → 赔偿单状态回撤（`cancelled`）。
     - `approved` → 赔偿单落定，把责任人扣款/记账信息写入 `AssetCompensation` 记录。
     - `!approved` → 赔偿单驳回，`reject_reason = instance.reject_reason`。
   - **若 `AssetCompensation` 实体尚未建**：本次仅**注册回调 stub**，函数体写一个 TODO + audit 记录，不落业务侧数据；提示"AP-21 待业务实体建模后完善"。这样至少幽灵单不再出现，未知 biz_type 分支消失。

### 验收
- 新增测试：`register_callback` 后 `_dispatch_callback` 能路由。
- 未注册 biz_type 走 finalize 时不抛，但产生一条 `approval_flow_callback_missing` audit。
- 回调抛异常时产生 `approval_flow_callback_error` audit 且异常传播（外层事务回滚，符合现状）。
- 原 22 条 `if/elif` 全部删干净，`_dispatch_callback` 主体 ≤ 15 行。

## 4. 超时/催办真正落地（**P1 · 能力缺失**）

### 问题
- 规则里都配了 `timeout_hours: 48/72`，但 `ApprovalInstance/ApprovalTask` 无 `deadline_at`/`due_at`。
- 前端 meta 里回去的 `rule_timeout_hours` 是纯装饰。
- `/approvals/{id}/remind` 只写 audit，无频控、无通知。

### 期望行为
1. 任务激活时按规则的 `timeout_hours` 计算并落 `due_at`。
2. 待办列表能按 `due_at` 排序、能过滤"已逾期"。
3. `remind` 30 分钟内同一实例只允许一次。

### 修改方案

1. **模型**：`ApprovalTask` 增字段 `due_at: Optional[datetime] = None`；`ApprovalInstance` 增字段 `next_due_at: Optional[datetime]`（= 当前 seq 所有 active task 的最早 due_at，冗余便于列表查询/排序）。
2. **迁移**：新增 alembic revision 添加两字段，允许 nullable，无需 backfill（老实例保持 None，视为无超时）。
3. **`_advance`**：激活任务时 `t.due_at = _now() + timedelta(hours=rule.timeout_hours)`；同时更新 `instance.next_due_at = min(active_due_ats)`。规则需要通过 `instance.rule_id` 反查 `timeout_hours`（一次查询即可，缓存在局部变量）。
4. **`_instance_to_item` / `ApprovalItemOut`**：meta 里增加 `due_at`、`overdue: bool`（= `due_at < now`）。
5. **`remind` 频控**：在 `_stub_act` / `_act_instance` 的 `remind` 分支前查 `AuditLog`，30 分钟内已有 `approval_flow_remind` 的 → 429。
6. **仅登记，不发通知**：本次先只落 due_at + 频控，不做定时扫描/推送（那部分单独一个需求）。

### 验收
- 新增测试：start_instance 后 `task.due_at` = created_at + 规则 `timeout_hours`。
- `overdue` 字段随时间正确翻转（测试里 monkeypatch 时间）。
- 30 分钟内二次 remind → 429。
- 现有测试全绿。

## 5. 代码清理（**P2 · 一并做**）

以下改动零风险，顺手清掉：

### 5.1 删除 `finance._refund_flow_instance`
**文件**：`backend/app/services/finance.py` 约 799–812 行。
- 它只查 PENDING 不查 BLOCKED，与 `approval_flow.find_open_instance` 语义不一致且重复。
- 全库搜引用，替换为 `approval_flow.find_open_instance(db, "refund", refund_id)`，然后删除该私有函数。

### 5.2 `_resolve_task_candidates` 里重复调用 `_flow_superuser_ids(db)`
第 1 条修完之后这些 admin 兜底已删，同时把用到 `_flow_superuser_ids` 的地方（如仍需的地方）局部变量存一次。

### 5.3 `_advance` / `withdraw` / `cancel_instance` 补 audit
现有 audit 只覆盖 `submit/approve/reject/countersign/withdraw/admin_act`。补：
- `_advance` 里节点被 G-08 跳过时 → `action="skip_g08"`, detail 含 seq/node name。
- `_advance` 里 blocked → `action="block"`, detail 含 reason。
- `cancel_instance` → `action="cancel"`, detail 含 reason（**注意**：该函数当前 user 参数不存在，用系统 audit 即 user_id=None，同 3.2 的 `_audit_system`）。
- `_superuser_reopen_for_act` → `action="admin_reopen"`。

### 5.4 `withdraw` 允许 admin
**文件**：`backend/app/services/approval_flow.py` `withdraw` 约 669 行。
```python
if instance.initiator_id != user.id and not _is_flow_superuser(user):
    raise HTTPException(status_code=403, detail="仅发起人或系统管理员可撤回")
```

### 5.5 `start_instance` 校验 assignees 完备
**文件**：`backend/app/services/approval_flow.py` 约 431–447 行。
在创建 task 循环开始前，先扫一遍 nodes：
```python
required_keys = [n.get("assignee_key") for n in nodes
                 if (n.get("type") or "").lower() == NODE_ASSIGNEE
                 and n.get("assignee_key")]
missing = [k for k in required_keys if not (assignees or {}).get(k)]
if missing:
    raise HTTPException(status_code=400,
        detail=f"规则 {rule.code} 需要指定人参数：{','.join(missing)}")
```
