# CRM+OKR 系统测试计划与测试用例矩阵

## 1. 测试目标

本轮测试判断当前系统是否形成“身份与权限 → 线索与客户 → 商机与合同 → 应收与回款 → 项目交付 → OKR 与绩效 → 员工变动与责任交接”的业务闭环，并核对 PRD、验收条件、高保真原型、前端、后端与数据库实现是否一致。

本轮只测试、取证和报告，不修改业务代码，不新增或修改自动化测试。确认缺口后，先给出建议测试缝与用例，待产品/研发确认后再进入修复和 TDD。

## 2. 验收依据与优先级

1. `需求分析/最终产物/PRD-CRM+OKR公司管理系统.md`
2. `需求分析/C系统需求/验收条件分析/acceptance-criteria-CRM+OKR公司管理系统.md`
3. 权限、业务规则、生命周期、异常边界和数据模型分析文档
4. `高保真原型/` 中的原型说明、页面和交互
5. 当前前端、后端、数据库迁移与种子数据
6. README 仅作为运行说明；若与最终 PRD 冲突，以最终 PRD 和验收条件为准

已知需求冲突：最终 PRD 的 FR-013/FR-014 要求普通员工不可见未分配池且“不产生任何员工自行领取入口”，但权限文档 7.2、验收 AC-US-005/007、PAC-004 又要求开放窗口抢领和 20/100 条限额。本轮同时测试“管理层分配”和“员工抢领”，报告标记为“需求口径冲突”，不擅自判定唯一正确行为。建议最终统一为“普通公共线索可在授权开放窗口抢领；重点/未开放线索仅管理层可见和分配”，并明确两类池的字段与状态。

## 3. 端到端领域模型

### 3.1 核心对象和上下游关系

| 上游对象 | 关键状态/事实 | 下游对象 | 闭环约束 |
|---|---|---|---|
| 员工、部门、岗位、角色 | 在职、转岗生效、离职交接、停用 | 菜单、数据范围、业务责任 | 权限按生效时间变化，历史责任不丢失 |
| 线索 | 草稿、待查重、待分配、已分配/保护中、跟进中、已释放、已转化、作废 | 客户、联系人、商机 | 查重、唯一主负责人、分配/领取/释放/退回留痕 |
| 客户、联系人 | 唯一主体、多个联系人、主负责人 | 商机、合同 | 不同联系人不误合并，负责人交接保留历史 |
| 商机 | 初步接触、需求确认、方案报价、谈判、赢单/输单/暂停 | 合同、成交移交 | 赢单后承诺、范围、责任与来源连续 |
| 合同 | 草稿、审批中、生效、履约、完成/终止 | 应收计划、项目启动 | 客户、商机、金额、范围、法务/财务审核完整 |
| 应收、收款、核销 | 待收、部分收、已收、逾期；到账待核验/已确认 | 项目财务条件、利润 | 销售不可确认到账；回款不能超额或重复核销 |
| 项目 | 待立项、审批、立项、计划、执行、暂停、待验收、结项/取消 | 基线、任务、工时、变更、成果、验收 | 财务条件、资源承诺、版本化基线和验收证据不可跳过 |
| 项目任务、工时 | 待接收、进行中、待确认、完成/退回；计划/实际工时 | 进度、成本、绩效证据 | 任务责任、时间重叠、重复工时和归属可校验 |
| 项目变更、验收 | 待审批、批准/驳回；通过/整改 | 新基线、结项、复盘 | 不覆盖原基线；未验收或财务未核对不得结项 |
| OKR/目标 | 草稿、制定、执行、自评、评价、校准、申诉、确认、归档 | 绩效结果、工资系数 | 公司→部门→个人对齐，证据、评分和规则版本可追溯 |
| 绩效结果 | 初评、校准、员工确认/申诉、锁定 | 绩效工资系数 | 未结申诉不得锁定，固定工资不受影响 |
| 员工变动/交接 | 待生效、交接中、生效/取消 | 客户、线索、项目、任务、工单、知识、审批 | 业务交接完成后停用；转岗同步数据范围和审批关系 |

### 3.2 关键不变量

- 身份不变量：无有效 JWT、JWT 过期/伪造、离职停用账号不得访问受保护接口。
- 授权不变量：菜单隐藏不能替代后端鉴权；公司/部门/个人数据范围同样作用于列表、详情、搜索、导出和关联查询。
- 幂等不变量：重复点击、刷新、超时重试不得生成重复线索、跟进、合同、收款、核销、任务、工时、评分或交接。
- 财务不变量：商务不能确认到账；收款确认与核销分离，累计核销不得超过收款或应收余额。
- 项目不变量：未满足合同/财务/资源条件不得正式启动；未批准变更不改基线；未验收与未财务核对不得结项。
- 绩效不变量：无生效规则/证据/对齐关系不得完成评分；未结申诉不得锁定；系统管理员不得代替综合管理或财务。
- 历史不变量：关键业务更正使用撤销、冲销或新版本，不静默覆盖原记录。

## 4. 测试策略

- 静态一致性：建立 PRD FR/AC/PAC/PATH 到前端路由、API、服务、ORM、迁移和现有测试的映射。
- API 测试：使用真实 FastAPI、真实测试数据库和 JWT，覆盖成功、401、403、404、409、422、重复提交和数据范围。
- 页面 E2E：用应用内浏览器运行真实前后端，验证导航、表单、状态反馈、刷新恢复、网络错误和跨页面闭环。
- 数据核对：通过公开 API 和只读数据库查询核对状态、关联、唯一性、金额、版本与审计轨迹。
- 根因诊断：每个失败先建立可重复、可自动运行的最小复现，再检查路由、服务、模型、迁移和前端调用。
- 回归验证：执行后端全量 pytest、迁移校验、前端类型检查与生产构建，再复跑核心页面冒烟。

## 5. 严重程度

| 级别 | 判定 |
|---|---|
| S0 阻断 | 系统无法启动/登录，数据破坏，广泛越权，核心闭环完全不可用 |
| S1 严重 | 财务/权限/关键状态错误，核心业务无法闭环，错误成功或不可恢复重复数据 |
| S2 主要 | 重要分支缺失或行为错误，但存在替代路径或影响局部角色 |
| S3 次要 | 展示、提示、易用性或非关键边界问题 |

## 6. 结果分类

- A：需求正确且实现正确
- B：需求存在但尚未实现
- C：页面存在但后端没有闭环
- D：功能存在但行为错误
- E：正常流程通过但异常流程失败
- F：缺少自动化测试覆盖
- R：需求口径冲突/暂不可判定

## 7. 测试数据与角色

至少准备：系统管理员、管理层、部门负责人 A/B、普通员工 A/B、销售、商务、财务、项目负责人、项目成员、综合管理人员；至少两个部门；一个离职用户；一组同手机号/同公司不同联系人/同名不同手机号线索；一个完整成交合同；部分收款和超额收款；一个跨部门项目；一个存在未批准变更和未完成验收的项目；一套公司/部门/个人 OKR；一个待申诉绩效；一个待转岗和待离职员工。

如当前种子数据不具备上述角色/对象，本轮优先通过公开管理页面/API创建；若能力本身缺失，则记录为前置能力缺口，不直接改库伪造业务成功。

## 9. 自动化覆盖预期

建议的公开测试缝（本轮仅评估，不写测试）：

1. 身份缝：`POST /api/v1/auth/login`、`GET /auth/me`、菜单接口及受保护 API。
2. 业务 API 缝：线索、客户、商机、合同、收款、核销、项目、工时、OKR、绩效、组织员工公开 REST 接口。
3. 状态机缝：所有状态变更端点，断言允许/禁止转移、版本与审计。
4. 浏览器缝：登录、PATH-002、PATH-003、PATH-004、PATH-007、PATH-008 的关键页面旅程。
5. 迁移缝：空库迁移到 head、种子幂等、SQLite 测试数据库约束。

自动化覆盖至少包括：每个核心端点一条正常用例、一条无权限用例、一条规则/状态冲突用例；金额和状态不变量使用参数化/属性测试；重复提交和并发使用集成测试；页面只保留少量关键闭环 E2E。
