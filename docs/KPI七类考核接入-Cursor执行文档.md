## 1. 目标与完成边界

将七份文件对应的业务纳入现有 `/api/v1/performance` 模块，以后端接口实现以下流程，并用独立原型表达未来界面：

1. HR 建立模板草稿，查看原始规则和冲突，补全参数后提交审批，批准版本生效。
2. 同一自然月可以对不同员工使用不同部门/岗位模板；同一员工的月度绩效与入职阶段考核可以并存。
3. 业务数据进入指标台账，系统展示目标、实际、证据、计算过程、待补数据和预估分。
4. 员工核对，主管评价，指定人员复核，员工确认/申诉，最终归档。
5. 按考核单冻结的结果政策生成绩效工资计算依据；培训、观察期结果进入人事待处理流程。

“能录入七份表”不等于完成：应能解释每项分数、追溯每项事实、保留版本，并在规则不完整时明确阻止错误出分。

本次不强制增加 OKR 权重。七份表中未规定 OKR 占比的，按原表 KPI 规则执行。既有 OKR 考核和历史绩效继续使用旧引擎。

### 2.1 必须解决的现有约束

- `PerformanceCycle.period_label` 全局唯一，周期只有一个 `default_template_id`；`generate_assessments` 将其用于所有员工。同月多岗位应通过“周期内人员模板分配”实现，不能以每部门新建同名月份规避。
- 当前生成逻辑用 `(cycle_id, user_id)` 判断已存在，入职阶段和月度考核会互相排斥。新增考核类型与实例键，数据库唯一约束和生成查询同步改造。
- 当前 `compute_weighted_score` 对各项评分求加权平均。原表的“20 分指标拿 15 分”不能直接输入旧项分数再乘 20%，否则会二次折算。
- 当前 `score_rule` 是字符串，取数器没有执行这些文字规则。录入“每少一个扣五分”不会自动产生该行为。
- 当前 `_grade_and_coeff` 和 `resolve_grade` 阈值不同，`GRADE_COEFF` 为 1.20/1.10/1.00/0.85/0.70；与多数原表的 1.00/0.80/0.60/0 不一致。
- 当前 `_bonus` 使用固定 5000 作为计算基数。新模板必须从已确认的员工绩效基数读取，缺基数时只能显示待补，不能沿用该常数。
- 当前 `customer.deals` 统计赢单商机的 `expected_amount`，不是签约客户数，也不能直接视为财务确认成交额。`customer.payments` 使用周期已确认回款/周期应回款，需保留其原有口径，另建新指标时明确分子、分母。
- 当前分数优先顺序允许主管覆盖系统分，未评分项在旧计算中可能变为 0。新引擎必须区分“已确认零值”和“未提供数据”，系统结果更改需理由及复核记录。
- 考核归档、审批回调、申诉、工资生成均涉及结果更新，不能只替换评分页的公式。

## 6. 统一计算模型

### 6.1 三种计分模式

- `legacy_weighted`：既有模板继续走当前计算，保留历史行为。
- `points_sum`：本批市场、运维、制作、品宣、直播及培训使用“各项实际分相加”。培训各维度满分取权重数值。
- `event_ledger`：讲师采用起始分100+已确认加分-已确认扣分。

新模式每个指标定义 `max_points`，`awarded_points` 是该指标实际贡献分，不再乘权重。基础分为各项贡献分之和。`weight` 仅用于旧模式，不为新模式校验100；新模式改为校验基础满分与模板标称满分一致。专项调整使用独立分录。

总分=基础分+批准的专项调整；最终等级再应用已确认的强制等级规则。小数使用Decimal和`Numeric`，不得先四舍五入成整数后判断等级。保存2位分数；原表档位边界待确认后按连续区间定义，例如[90,100)，避免89.5无档位。所有正式阈值按批准版本执行。

### 6.2 规则类型

支持 `manual_points`、`shortfall_deduction`、`ratio_bands`、`proportional`、`event_deduction`、`composite`、`conditional_override`。规则用受限JSON与Pydantic判别联合校验，不使用eval，不运行输入中的代码。

示例仅对应市场签约指标已描述的计分方式；客户去重和签约状态口径仍须确认：

```json
{
  "metric_key": "market.signed_clients",
  "max_points": "20",
  "unit": "customer",
  "target": {"kind": "fixed", "value": "4"},
  "rule": {"type": "shortfall_deduction", "points_per_missing": "5", "floor": "0", "cap": "20"},
  "source": {"kind": "system", "ref": "contract.signed_customer_count"}
}
```

上述`source.ref`为拟新增，不是现有数据源。

规则执行顺序：数据完整性→适用性→目标计算→基础规则→跨指标覆盖→专项调整→等级覆盖→结果系数。客资达标覆盖视频/播放应生成可见计算明细。若原始数据缺失，不能用覆盖规则掩盖缺证，除非批准模板明确无需该数据。

跨指标依赖只允许同一考核单内的稳定指标键，发布时校验引用存在、禁止循环、执行顺序稳定。人工例外不可覆写原始数据；以带理由和复核记录的调整保存。

### 6.3 结果政策

| 适用模板 | 原表结果政策 |
|---|---|
| 市场、运维、制作、直播 | 优秀90及以上系数1.00；良好80至不足90系数0.80；合格60至不足80系数0.60；不足60系数0 |
| 品宣 | 90及以上优秀，额外奖金未定义；70至不足90全额绩效；60至不足70系数0.80；不足60系数0.50。优秀基础绩效系数须在正式发布前确认 |
| 培训 | 75分合格；人事结果，不参与月度绩效工资重复计算 |
| 讲师 | 主制度缺失；积分、观察期结果与工资处理分开 |

市场原文“90分以上”与其他表“90—100”须在发布确认中明确90端点。上表连续区间是拟配置表达，应保留确认记录。

绩效金额=考核单冻结的员工绩效基数×模板结果系数。基数来源在实施时核对`services/hr.py`和员工薪酬字段；没有可信来源时新增受权限控制的基数录入，不默认5000。已有已发布工资条不回算；同月只能一份主月度考核参与常规绩效工资，阶段考核不参与。

## 7. 数据模型设计

所有字段名为实施建议，可按项目命名微调，语义和约束必须保留。使用Alembic增量迁移；新字段对旧记录可空或有兼容默认值。对PostgreSQL与测试SQLite均验证。

### 7.1 扩展现有对象

**PerformanceTemplate**：增加`family_code`、`version`、`supersedes_id`、`engine_version`、`assessment_kind`、`scoring_mode`、`effective_from/to`、`definition_json`、`blocking_issues_json`。现有`code`保持唯一，建议版本化如`MARKET_MONTHLY_V1`。部门派生`base_template_id`不充当版本号。批准版本不可变，修订创建新行。

**PerformanceTemplateItem**：增加稳定`metric_key`、`max_points`、`unit`、`target_config_json`、`rule_config_json`、`source_config_json`、`source_provenance_json`。原有`score_rule`仅作旧兼容/人类可读摘要。新模式内部`weight`可空，但先检查旧客户端契约；旧接口不得无提示返回会使现有前端崩溃的数据。需要新结构时用显式版本化响应/新增详情端点承载，不为兼容伪造权重或把原始得分冒充百分制分数。

**PerformanceAssessment**：增加`assessment_kind`（monthly/onboarding/lecturer等）、非空`instance_key`、`engine_version`、`template_snapshot_json`、`period_start/end`、`due_at`、`data_cutoff_at`、`base_points`、`adjustment_points`、`total_points`、`grade_label`、`result_policy_snapshot_json`、`performance_base_snapshot`、`payroll_eligible`。旧分数字段继续保留，新模式由新字段对外展示，旧汇总为兼容缓存。等级code与中文label分离。

唯一约束为`(cycle_id, user_id, instance_key)`：普通月度用`monthly_primary`；入职阶段用`onboarding:{hire_event_id}:{stage}`。迁移前检测旧重复数据并出报告，不能静默删记录。讲师月度作为该人的主月度考核，不再重复创建普通月度单。

**PerformanceAssessmentItem**：冻结模板结构化字段；增加`awarded_points`、`data_state`、`calculation_trace_json`、`evidence_summary_json`、`revision`。实际值要能保存分子/分母、数量、项目明细，使用结构化数值字段/JSON，不将“30万”作为计算输入。

**PerformanceCycle**：保留月份唯一性，新增结构化`scope_json`替代依赖临时`_scope`或`str(scope)`；保留默认模板作为兜底。阶段考核实际取数区间存考核单，不能由自然月标签推断。

## 8. 数据接入与冻结

### 8.1 指标源注册表

新建`backend/app/services/performance_metric_registry.py`，声明每个来源的单位、支持维度、必需字段、计算窗口、是否可自动计算。接口说明规定未来前端从服务端注册表选来源，原型用对应合成数据表达选项。示例拟新增：

| 来源 | 首期路径 | 必须核对 |
|---|---|---|
| 有效线索、签约客户、新客 | 核实lead/customer/contract模型后聚合 | 有效状态、客户去重、归属变更、生效时间 |
| 拜访、邀约、私域、协会 | 审核台账/CSV；已有业务字段能覆盖时复用 | 客户唯一标识、实际到访与仅邀约的区别 |
| 视频产出及播放、点赞、转发 | 内容事实/CSV | 内容ID、账号、发布与数据采集时间；累计快照不能重复相加 |
| 直播GMV、订单人数、观众、时长、费用 | 场次事实/CSV | 场次ID、退款口径、人数定义、分钟/小时转换 |
| 续约 | 合同/项目事实，可先审核录入 | 应续约集合、到期日、998分类、续约关联 |
| 客诉 | 工单有明确投诉分类时引用，否则新事实台账 | 已核实、责任归属、软件原因排除；普通工单不能算投诉 |
| 服务响应 | 有消息/跟进时间事实时计算，否则审核超时事件 | 工作时间日历、首次有效回复、超时规则 |
| 学习、讲师、面谈 | 配套反馈和交付记录 | 活动有效性、评价人范围、评优评差核实 |
| 考勤 | 现有飞书日记录 | 缺卡不等于旷工；迟到早退同日是否计两次 |

客资可以按角色贡献规则同时支持不同岗位考核，但必须保存同一客户/线索来源与贡献角色；不能只按当前owner将全部历史贡献转移。跨部门贡献与单指标去重是两件事，规则须明确。

### 8.2 CSV 导入

首期实现两步：上传预览→明确确认入库。列包括员工标识、metric_key、发生日期、数值、单位、来源系统、source_record_id、项目/客户/内容/场次标识及证据引用。按指标提示额外必需列。模板CSV由系统导出，不要求用户手写metric_key。

解析中文UTF-8 BOM、空值、百分比与日期；未知员工/项目不能偷偷新建。值0保留为0，空值为missing。单行有错误默认整批不写入，返回行号/列名/原因。重复来源记录按稳定业务键去重，不能仅用上传文件hash；修改文件重复导入同一业务事件仍应识别。更正作为新revision，不重复累计。

导入和人工录入数据须经审核后参与正式考核。预估结果可展示未审核事实，但必须明确标记，不能用于归档。

### 8.3 数据冻结时点

生成考核时冻结规则、人员归属、项目责任、目标与考核窗口，实际数据形成可更新的预估版本。发布供员工确认前执行一次取数快照；确认/复核针对该revision。

归档使用已确认快照。若归档前发现来源变化，只提示差异并走刷新、重新确认，禁止静默重抓数据改变已审批分数。锁定后只可通过申诉/更正生成新revision；已发薪的更正走已有工资条修订机制，不覆盖原批次。
