# KPI 考核原型交付说明

版本日期：2026-10-06。入口为本目录的 frontend.html，无需构建。保留同目录 CSS、JS 文件，直接打开 HTML 即可；也可通过静态服务器访问。默认首页为企业知识库，点击 KPI 考核进入管理员工作台。

原型用于确认页面、角色分工和交互流转，使用虚构员工与示例数据。提交、评分、复核、归档只改变当前页面会话；刷新恢复示例进度。员工与主管手动保存的草稿缓存到当前浏览器。附件只记录文件信息，不实际上传，刷新后须重新选择。正式系统的数据、身份、权限和文件存储须由服务端提供。

## 一、直接查看各页面

在静态服务器地址后拼接以下入口；也可打开 frontend.html 后在地址末尾添加对应查询参数。

| 视角 | 原型入口 | 核心任务 |
| --- | --- | --- |
| 管理员 / HR | frontend.html?view=kpi | 全局进度、发起考核、HR 复核 |
| 往期考核 | frontend.html?view=kpi&page=history | 历史成绩、变化、筛选导出 |
| 模板管理 | frontend.html?view=kpi&page=templates | 指标查看、复制版本、配置草稿 |
| 主管 | frontend.html?view=kpi&role=manager&page=team | 直属团队与待评分列表 |
| 主管评分 | frontend.html?view=kpi&role=manager&page=scoring&person=person-0-1 | 王芳的材料、评分和反馈 |
| 员工 | frontend.html?view=kpi&role=employee&page=self | 张明本人填报、提交记录、结果确认 |

右上角“原型体验身份”仅用于切换陈悦、李岚、张明三个示例身份。正式系统从登录用户及权限生成入口，不能把此下拉框、URL 的 role 或 person 当作身份认证。员工查看本人考核；主管查看由其负责评分的员工；管理员按组织权限查看管理范围。同一用户有多项职责时可具有相应的多个工作入口。

## 二、页面与权限

| 功能 | 管理员 / HR | 主管 | 员工 |
| --- | --- | --- | --- |
| 发起考核、分配模板和人员 | 有权限时可操作 | 不展示 | 不展示 |
| 本期进度 | 管理范围内全部人员 | 自己负责的团队 | 本人记录 |
| 员工材料 | 查看 | 查看所负责员工的提交材料 | 本人待提交时编辑 |
| 模板标准、权重 | 本期快照 | 只读 | 只读 |
| 实际完成情况 | 查看 | 材料只读，核实后评分 | 待提交时自行填写 |
| 保存填报草稿、提交 | 不代员工操作 | 不代员工操作 | 本人操作 |
| 评分、主管反馈 | 查看，不替主管评分 | 当前允许评分时操作 | 只读查看 |
| 退回员工补充 | 本次 HR 页不提供 | 待评分时填写原因 | 查看原因并重新填报 |
| HR 复核、退回评分 | HR 待复核时操作 | 接收修订要求 | 查看进度 |
| 最终结果确认 | 查看进度 | 查看进度 | 本人待确认时操作 |
| 已归档记录 | 可见范围内只读 | 团队记录只读 | 本人记录只读 |

员工页采用“指标填报 + 完整度检查 + 固定操作栏”；主管采用“团队待办 → 独立评分页”；管理员采用“部门进度 + 人员清单 + 复核详情”。角色之间既有不同入口，也有不同数据范围和操作权限。

## 三、考核流转

正常流转：管理员发起 → 员工填报 → 主管评分 → HR 复核（可选）→ 员工确认 → 归档完成。

| 原型状态 | 线上接口状态参考 | 当前处理人 | 可执行操作 | 成功后 |
| --- | --- | --- | --- | --- |
| submit | employee_pending | 本人 | 存草稿、提交材料 | scoring |
| scoring | manager_pending | 分配的主管 | 存评分草稿、提交、退回补充 | review 或 confirm；退回为 submit |
| review | hr_pending | HR | 通过、退回主管 | confirm；退回为 scoring |
| confirm | employee_confirm_pending | 本人 | 查看评分、确认结果 | done |
| done | completed / 已锁定、已归档 | 无待办 | 只读查看 | 不允许修改 |

线上状态必须以接口返回为准，不能由前端自行改名后写回。旧的 pending_self、pending_manager 等兼容状态也需要适配。

草稿是未提交内容的保存状态，不等于提交成功。退回补充在原型中为 submit + returnInfo；HR 退回评分为 scoring + hrReturnInfo，分别记录具体原因及处理记录。正式 DTO 如何表达须与后端统一。

退回员工时保留成果说明、链接和附件信息，清空本次核对确认，新一次提交增加提交版本。退回主管时保留各指标得分和评分依据，重新要求主管核实确认。未启用 HR 复核时，主管提交直接进入员工确认。

## 四、员工页：我的考核

顶部显示周期、本人、岗位、固定模板版本、主管及截止时间；阶段条说明当前环节。桌面中间为可滚动填报区，右侧为完整度检查和提示；底部操作固定。手机保留单列可滚动内容、固定底部操作及必填项完成数。

指标显示名称、目标标准、满分权重和证明要求。当前原型由员工自行填写各项实际完成情况，并补充说明和材料；模板标准和权重只读，显示本期快照，不能以新模板覆盖旧考核。

若正式系统已有系统取数指标，应按后端指标配置带入并只读；当前员工手填原型未演示该分支。指标名称或来源文字含 CRM 不等于自动取数开关，不能仅按来源文字决定字段是否可编辑。

原型校验规则：

- 每项需有实际完成情况与成果说明。
- 首项至少提供有效链接或本次选择的附件，其他证明选填。正式系统从指标/材料任务配置读取要求，不能在业务代码中写死第一项。
- 链接仅接受有效 HTTP / HTTPS 地址。
- 工作总结必填，提交前必须勾选核对填报内容及材料完整。
- 支持 PDF、DOC/DOCX、XLS/XLSX、PNG、JPG/JPEG；单个不超过 10 MB，每项最多 5 个。正式系统以文件服务配置为准。
- 完成数为符合填写要求的指标数加工作总结，不含确认勾选。字段完整不等于主管已核实材料。
- 草稿允许不完整；提交必须校验全部必填内容。

提交前确认对象及完整度；成功后同页切换只读记录，不再出现保存草稿、提交主管。当前处理人为主管或 HR。未复核得分标为主管拟评分；复核通过或无需复核时进入结果确认，展示各项得分、总分和主管反馈。

## 五、主管页：团队考核与独立评分

默认打开待我评分，可切换全部团队，搜索员工或岗位。只展示考核单分配给该主管的员工，不通过前端拿到全公司名单后自行筛选权限。李岚样例负责市场部 6 位员工，不能打开 AI 运维员工评分单。

去评分打开独立页面：顶部为员工、模板版本与截止日期；逐项把标准、完成情况、成果说明、链接和附件放在评分输入旁；员工材料和权重只读，总分自动汇总。

每项得分在 0 到该项满分之间，最多一位小数。评分草稿可不完整；提交时各项得分、评分依据、材料核实确认均必填。材料不足应写明具体原因并退回，不直接替员工修改。

提交弹窗明确总分和下一处理人。提交后评分锁定；HR 退回时恢复修改入口并显示修订原因。待员工补充、HR 复核、员工确认、已完成等状态打开只读记录页。

正式团队列表需支持分页；当前团队样例只有 6 人，全部显示。评分页退回补充、保存评分草稿、提交评分固定在底部。手机也须保留这些操作。

## 六、管理员与模板页

统计、部门进度和人员列表均来自同一组考核数据。筛选不改变全期统计口径，列表计数反映筛选结果。点击统计或部门进度筛选人员；详情只读查看材料与评分，HR 待复核时提供通过和退回主管。

发起向导分三步：选择已发布模板并核对人员 → 设置截止日期及 HR 复核开关 → 核对后确认。选中部门至少一人，人员不可重复发起同周期考核；日期在考核月结束后，按提交、评分、复核（启用时）、确认排序。示例截止日期是固定演示数据，不进行真实逾期拦截；线上逾期策略由制度和后端配置决定。

发起固定人员、主管、指标和模板版本快照。新周期不复制旧周期的材料、评分、退回原因和记录；模板修订不影响已发起考核。

往期按周期、员工、部门筛选，只读查看；导出按当前筛选范围生成。空结果提供原因和继续操作的入口。

模板页支持查看、新建草稿、复制修订、权重校验。原型的发布动作为交互简化；正式开发必须保留现有“提交审核 → 审核通过 → 发布”流程，复用 submitTemplateApi / approveTemplateApi / publishTemplateApi，不能绕过审核。本次没有重绘模板审核子页面，旧完整流程保留在 frontend.html?view=kpi&experience=classic。

## 七、现有接口与缺口

已检查本项目 frontend/src/api/performance.ts 的封装，以下是已有调用定义，不表示本次原型已接入或验证后端实现。

| 操作 | 优先复用封装 |
| --- | --- |
| 本期部门和人员进度 | fetchAssessmentBatchesApi、fetchAssessmentBatchDetailApi |
| 匹配人员、批量发起 | matchPersonnelApi、createAssessmentBatchApi |
| 员工本人列表 | fetchMineAssessmentsApi |
| 主管团队列表 | fetchTeamAssessmentsApi |
| 运行期详情 | fetchRuntimeDetailApi |
| 允许操作 | runtime-detail.allowed_actions、fetchAssessmentActionsApi |
| 材料任务、草稿、单条退回、核实 | fetchMaterialTasksApi、saveMaterialDraftApi、returnMaterialApi、verifyMaterialApi |
| 员工草稿和整份提交 | employeeSubmitApi，以 draft 区分 |
| 主管提交 | managerSubmitApi |
| HR 通过或退回 | hrReviewApi，以 approve 区分 |
| 员工确认 | resultConfirmApi |
| 往期 | fetchAssessmentHistoryApi，按权限设置 scope |
| 模板查询、验证、修订、审核、发布 | 对应现有 TemplateApi 封装 |

运行期操作携带最新 revision，批量发起使用 Idempotency-Key。成功后重新取详情、允许动作和汇总。失败保留输入并显示原因，不能先标成功再等待接口；版本冲突提示刷新，不静默覆盖。

需与后端确认或补齐：

1. **主管评分草稿**：managerSubmitApi 类型没有草稿标记，须明确草稿接口；不能用提交接口假装暂存。浏览器缓存只是原型实现。
2. **整份退回员工**：现有封装有单条材料退回，需确认能否完成整份考核回到员工填报的流转，或补充整份退回接口。
3. **逐项成果说明、链接和附件**：当前员工提交主要是 actuals / self_comment / draft；逐项证明须映射材料任务或扩展 DTO，统一说明字段、链接和附件 ID，不能任意拼进实际完成值。
4. **文件服务**：真实上传使用返回的附件 ID、访问权限和下载地址，上传完成才可提交。草稿中的文件名不等于已上传文件。
5. **身份与权限**：采用登录用户、user_id / manager_id 和 allowed_actions；URL 仅定位记录，服务端验证归属与当前动作。

申诉、旧绩效和其他已有业务能力不在本次角色页的绘制范围，不能因为原型没画出而删除。示例姓名、日期、状态代号、权重和数据源不作为线上固定配置。

## 八、布局与组件拆分

延续蓝灰白风格：主色 #2446B8，正文 #192B49，次要文字 #6B7C93，背景 #F4F6FA，成功 #218167，待补充用琥珀色。中文优先微软雅黑 / 苹方，标题 21–27px，主要表单内容 12–14px。

桌面管理页按窗口分配列表空间，最多 10 条，分页固定，矮屏减少条数。填报及评分页内部滚动，操作固定；手机单列展示。不要靠隐藏溢出来掩盖截断数据。

建议拆分权限导航、周期选择、统计/部门进度/人员清单、阶段条、指标填报、成果链接/附件、完整度、指标评分/总分、反馈输入、只读材料/结果、时间线，以及各确认和退回弹窗。

保留焦点、标签、错误提示及弹窗焦点循环。员工填报和主管评分有未保存修改时，原型在刷新或关闭前提示；同一会话的页面切换保留输入。正式系统也须保留离开保护，并按接口实现加载中、上传中、失败和版本冲突状态。

## 九、验收

1. 角色入口和数据范围正确，越权记录服务端拒绝，不能仅隐藏导航。
2. 员工不完整内容可存草稿，缺证明、无总结、未核对不能提交；当前原型实际完成情况手填，标准和权重只读。
3. 提交后员工页只读，主管待办及管理员汇总同步更新。
4. 主管单项分数合法、反馈完整，总分与各项一致。
5. 材料退回原因可见，内容保留，员工核对后再提交。
6. HR 退回保留分数及意见，主管修订后重新复核。
7. 通过后本人看到各项得分、总分及反馈；确认归档后关闭修改入口。
8. 不启用 HR 复核时直接进入员工确认。
9. 新周期材料和评分为空；旧记录保留发起时模板版本。
10. 往期及导出遵守范围；不同尺寸无横向溢出，固定操作不遮挡内容。

原型回归脚本为 kpi-workbench.smoke.cjs、kpi-employee.smoke.cjs、kpi-roles.smoke.cjs。知识库和旧 KPI 入口继续保留。正式开发需另验证接口权限、并发提交和真实文件上传。
