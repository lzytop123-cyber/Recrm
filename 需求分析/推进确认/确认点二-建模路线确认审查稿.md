# CRM+OKR公司管理系统：建模路线确认审查稿

## 1. 路线结论

建议采用“双轨分析”：结构化业务分析与面向对象业务分析并行覆盖，完成后执行业务模型一致性审查。

## 2. 选择依据

1. 系统同时包含线索到成交、合同收款、三类业务交付、跨部门工单、人员与会议排期、OKR绩效、工资衔接、员工生命周期和知识治理等多条流程。
2. 多个流程包含分派、确认、审批、同步、异常补偿、规则判断和跨部门责任，单纯对象分析无法充分说明业务如何流转。
3. 线索、客户、合同、项目、工单、会议、排期、员工、目标、绩效结果和知识等核心对象具有独立状态、关系和行为，单纯流程分析无法充分支撑数据、权限和系统功能设计。
4. 飞书知识与日历同步、财务与绩效衔接等跨系统或跨职责场景需要同时验证流程、对象状态和数据一致性。

## 3. 结构化业务分析范围

| 阶段 | 主要目的 | 本项目重点 |
|---|---|---|
| B1.1 业务过程分析 | 明确端到端流程、参与角色、输入输出和异常分支 | 销售、项目交付、工单、会议排期、绩效工资、员工生命周期、知识治理 |
| B1.2 数据流分析 | 明确业务信息在角色、流程和系统之间如何产生与流转 | 线索到项目追溯、绩效到工资、会议到飞书日历、知识来源到检索 |
| B1.3 数据字典与数据定义 | 统一核心业务概念和统计口径 | 客户主负责人、有效线索、回款、里程碑、排期冲突、绩效结果、同步状态 |
| B1.4 逻辑数据模型分析 | 明确核心数据对象及业务关系 | 客户、合同、项目、员工、会议、排期、目标、工单、知识的关联 |
| B1.5 决策与业务规则分析 | 固化可配置规则、判断条件和责任边界 | 线索抢领、项目审批、排期冲突、绩效工资、工单时限、会议同步 |
| B1.6 异常与边界分析 | 识别异常、补偿、冲突和边界条件 | 重复线索、收款异常、项目延期、人员冲突、同步失败、离职移交、越权访问 |

## 4. 面向对象业务分析范围

| 阶段 | 主要目的 | 本项目重点 |
|---|---|---|
| B2.1 用例分析 | 按角色明确业务目标和系统责任 | 管理层、部门负责人、销售、财务、项目、讲师、会议组织者、员工等角色 |
| B2.2 业务对象识别 | 识别具备业务身份和责任的核心对象 | 线索、客户、商机、合同、项目、任务、工单、会议、排期、员工、目标、知识 |
| B2.3 对象关系分析 | 明确对象之间的业务关系和约束 | 客户唯一主负责人、合同与项目、会议与讲师、员工与组织、目标与绩效 |
| B2.4 生命周期与状态分析 | 定义对象从产生到结束的状态变化 | 线索、合同、项目、工单、会议、员工、绩效结果、知识来源 |
| B2.5 对象行为分析 | 明确对象可执行的业务行为及责任角色 | 分配、领取、确认、变更、取消、锁定、移交、同步、下架等行为 |

## 5. 一致性审查

完成两条分析路线后执行B3业务模型审查，重点核对：

- 流程步骤引用的对象、状态和规则是否存在。
- 对象状态变化是否都能追溯到明确业务事件和责任角色。
- 结构化数据流与对象关系是否一致。
- 异常补偿是否能恢复流程与对象状态一致性。
- 会议排期、讲师占用与飞书日历，绩效结果与工资处理等跨域关系是否前后一致。

## 6. 本轮执行范围

本轮执行B1.1至B1.6、B2.1至B2.5及B3，不裁剪B层子阶段。各阶段只分析业务需求，不进入数据库表、接口协议、页面控件或技术架构设计。

## 7. 前置问题处理

中央问题池中与业务过程、规则和权限相关的后续问题将在对应B层阶段启动前处理。对于尚无公司标准流程的问题，由Codex先提出方案，用户确认后再作为正式建模输入。
